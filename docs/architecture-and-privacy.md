# 架构、隐私白名单与日志轮转详解

**中文** · [English](./architecture-and-privacy.en.md) · [返回文档中心](./README.md)

这篇文档把 `mindie-diagnostics` 最核心的四个设计机制讲清楚：**怎么记故障才不越界、公开上报时怎么保证绝对不泄密、为什么授权状态要跟文件损坏严格区分、以及本地日志怎么做到永远不撑爆硬盘。**

---

## 1. 谁的故障谁来记，不把普通报错当成组件 Bug

在 MindIE Agent 各个组件里，只有真正负责那一层逻辑的模块才会调用 `mindie_diagnostics.integration.record_failure`：

```python
from mindie_diagnostics.integration import record_failure

result = record_failure(
    "remote-dev",
    "mcp.request",
    stage="decode",
    category="protocol_mismatch",
    exception=error,
)
```

- **只收固定标签，不收用户输入**：`category` 和 `operation` 只能传代码里写死的静态名称，绝不允许把用户输入的命令或文件名塞进来。
- **记日志失败绝不耽误正事**：正常写入本地日志后会返回一个随机的 `incident_id`；万一本地磁盘满了写不进去，它只会在返回结构的诊断字段里标一下 `logging_failed`，**绝对不会把原本正常的业务结果搞崩，也不会偷偷去联网或调大模型**。
- **分清“用户日常报错”和“产品自身缺陷”**：
  - 平时参数传错了、配置文件没写、没权限、SSH 连不上、或者你跑的训练脚本自己报错退出（非零退出码），这些都是正常使用中会遇到的情况，不属于 MindIE 组件自身的 Bug——它们会被标为 `reportable=False`，只留在你本机方便你自己查，**绝不会往 GitHub 上提 Issue**。
  - 只有组件内部抛出未捕获异常、或者组件自己的协议解析坏了，才会被标记为可上报候选。

## 2. 公开上报的严格白名单：到底哪些能发、哪些绝对不发？

只有当你手动执行了 `reporting configure --enabled true` 并启动了后台 Worker（`reporting ensure`），系统才会在后台把组件自身的 Bug 整理成 GitHub Issue。整个过程**完全不用大模型**，而是用死板的白名单筛子过滤：

| 类别 | 具体字段 |
| --- | --- |
| **✅ 白名单允许包含** | 组件名称、组件版本号与 Git Commit 号、操作名与阶段名、固定的错误类别名、单调时钟耗时、进程退出/清理状态标记、MindIE 自身代码的栈文件名与行号 |
| **🚫 绝对剔除（永不上传）** | 原始异常报错文本（`str(e)`）、执行的 Shell 命令、标准输出与标准错误（`stdout`/`stderr`）、Prompt 提示词、聊天记录（Transcript）、环境变量值、密码与密钥、会话/作业 ID、业务文件路径、远端服务器 IP 与主机名 |

**防刷屏与随时撤回机制**：
- **绝不盲目重复建单**：每条待报故障最多尝试 3 个处理周期。如果某次发请求时网络断了、不确定 GitHub 上到底建没建成功，下一轮只会先去查重对账，绝不无脑再发一遍。如果仓库里已经有相同指纹的 Issue（不管是 Open 还是 Closed），只会安静关联，不会去乱发评论或把已关闭的 Issue 重新打开。
- **关掉开关立刻撤回**：待发送队列最多存 1,000 条（保留 7 天），已完成的回执最多存 1,000 条（保留 30 天）。只要你执行 `configure --enabled false` 关掉自动上报，**队列里还没发出去的所有记录立刻作废**；就算以后你再次打开开关，以前关掉期间攒下的旧记录也绝不会翻出来补发。

## 3. 为什么把“用户没授权”和“配置文件读不了”分得这么清？

很多劣质工具在读取配置文件报错（比如文件损坏或权限不对）时，会直接 `except: return None`，把它当成“用户第一次用”或者“用户关掉了开关”——这会导致状态被悄悄重置甚至乱删数据。

`mindie-diagnostics` 严格区分这三种情况（`consent_status()`）：
1. **`allowed`（已明确允许）**：配置文件完好，且用户开启了自动上报。
2. **`withdrawn`（用户未开启或已撤回）**：配置文件不存在，或用户明确设为了 `false`。只有确认是 `withdrawn` 时，才会清空作废待发队列。
3. **`unavailable`（配置文件损坏或权限异常）**：`fallback.read_policy()` 发现文件存在但格式坏了、权限不安全或读不出来时，会直接抛出 `PolicyUnavailable`。此时系统会**暂停一切对外网络发送，但完整保留待处理队列和日志游标**，等你修好配置文件再说，绝不乱删现场。

同样地，本地发送队列数据库（Outbox）带有专门的初始化标记。如果发现之前已经建好的数据库突然不见了或者变成了空文件，系统会明确报告存储故障，而不会偷偷新建一个空库假装一切正常。

## 4. 本地循环日志与离线维护（永远不撑爆硬盘）

- **4 × 1 MiB 环形分段写入**：
  每个进程/组件在本地只维护 4 个固定 `1 MiB` 大小的 JSONL 日志分段。写满一个就切下一个；只有当所有登记过的读取器都读完了某个旧分段，才会把它清空重用。如果磁盘空间紧张，会明确记录丢弃条数并报 `logging_failed`，等空间恢复后自动继续。
- **背压（`retention-state.json`）的真实触发条件与代价**：
  上一次离线维护只要判定该日志根目录**仍然超限**就会置位背压，而超限不只看总字节：**128 MiB / 512 个文件**任一仍超限，或本次扫描未能完整走完，都会置位。7 天只用于判断已消费旧分段能否回收，文件年龄本身不会置位背压。由于日志分段按进程命名（`<pid>-<hex>.jsonl`），而**文件数**随短生命周期进程数增长（不随字节数增长），所以在远少于 128 MiB 的占用下也可能触发背压。背压期间**新启动的进程无法新建自己的分段**，其本地故障记录会如实返回 `logging_failed` 并被丢弃（已有分段的进程则继续在自己的配额内滚动复用）。这是刻意保留的有界性取舍：文件数预算同时约束 inode 与每次扫描开销，取消它会允许十几万个小文件挤在 128 MiB 以内。背压会在下一次成功的离线维护（上报器已消费完积压、分片可被回收）后自动解除；因此**当上报策略文件损坏导致离线维护无法执行时，背压不会自动解除**，需要先修复或移除该策略文件。
- **零依赖启动兜底**：
  在完整日志器还没初始化好之前的极早期启动故障，会写进一个单独限制为 `1 MiB` 的兜底文件里。
- **离线维护命令（`reporting maintain`）与后台轮询准入边界**：
  - 默认把每个日志根目录控制在 **7 天以内、总大小不超过 128 MiB、文件数不超过 512 个**。
  - 默认完全离线运行；只有当你显式加上 `--update-running`、且后台刚好有一个正在健康运行的旧版本 Worker 时，才会把它平滑升级到新版本（如果 Worker 本来就是停着的，绝不会擅自把它拉起来）。
  - 客户端适配器通过 `--budget-seconds` 为阶段准入分配预算（默认 75 秒，当前按 `max(75, _UPDATE_BUDGET_S + 15)` 截断为 195 秒）。摄取扫描提前预留 3 秒结算时间（`_SETTLEMENT_RESERVE_S = 3.0s`），剩余时间不足该预留时不再启动新的日志根目录扫描或保留清理阶段；同理，后台 Worker 收到停止信号（`SIGINT`/`SIGTERM`）时也会在两条完整记录之间截断当前 `ingest` 扫描、保留已落盘游标，并停止准入后续阶段（记为 `limited` + `degraded`）。**需要注意：取消信号与截止时间都只是“停止新阶段准入 + 保留已完成游标”的协作边界，既不构成 `reporting maintain` 的 75 秒总耗时硬上界，也不证明整个操作系统级后台服务一定能在 20 秒（如 systemd `TimeoutStopSec=20`）内完成停机**——已进入的合法 SQLite 锁等待（3–5 秒）或已在执行中的子阶段仍可能晚于截止时刻结束。
